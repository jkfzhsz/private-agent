# 自我改动连续性优化方案（2026-09-29）

> 触发：蒋先生反馈"使用 PA 自我改动的过程中，每次涉及核心代码的修改，都会导致连接断开、
> 后续进程不可见，导致修改失败"。
>
> 本文为**诊断 + 优化方案**，未实施。

---

## 一、现象（2026-09-29 蒋先生补充修正）

| 项 | 描述 |
|---|---|
| 触发条件 | **仅当改动"核心代码"时**发生（非核心改动正常） |
| 断连时机 | **自我改动一开始就断联**，**不会出现"改完告知重启"这一步** |
| 可见性 | 改动在**后台**进行，用户**无法判断何时可以重启**；重启有时会打断后台进程 → 自我更新失败 |
| 归因 | **用户无法判断失败原因** |

> 初版方案曾误判为"改完 → 提示重启 → 用户重启才断连"。经蒋先生纠正后重新取证，
> 实际是**改动过程中后端异常退出**（见 §2.1），断连发生在流程**中途**而非结束。

## 二、取证（全部为代码 / 文件事实）

### 2.0 决定性现场：16:27 那次异常退出

`backend/logs/agent.log`：

```
16:27:28.978  user_message step=9/run_turn_start_r1 session=102   ← 自我改动开始
              （此后 3 分 16 秒零记录，且【没有】run_turn_done_r1）
16:30:44.228  Sidecar started: host=127.0.0.1 http_port=8765      ← 后端重启
16:31:47.484  user_message step=1/enter session=102               ← 用户重试
```

两条关键判据：

1. **全日志中 `Sidecar shutdown` 记录数 = 0** —— 按项目自带判据（`main.py:2482`：
   "有 shutdown 记录 = 优雅退出；只有 `Sidecar started` = 崩溃或强杀"），
   **16:30:44 那次重启是崩溃/被强杀，不是用户手动重启**。
2. **崩溃现场零痕迹** —— 无 sidecar 专属日志文件；子进程 stdout/stderr 从不落盘；
   运行期 `exit` 不记录退出码/信号；崩溃后的自动重启完全静默。

**→ 这就是"无法判断失败原因"的直接成因：崩溃现场被丢弃了。**

### 2.0.1 另一处真实隐患（同批修复）

`main/sidecar.ts` 原 `stdio: ["pipe","pipe","pipe"]`，但**只有 stderr 注册了
`on("data")`，stdout 从不被读取** → 管道缓冲区写满后子进程会阻塞在 write 上
（日志量大时尤甚）。已显式消费。

### 2.2 PA 没有自重启能力

```
grep -rniE "restart|self_restart|reload" private_agent/tools/**/*.py
→ 无任何自重启工具
```

**结论：PA 改完核心代码后，自己无法让改动生效，只能请用户重启 PA。**

### 2.3 Python 的固有约束

后端 sidecar 以 `python -m private_agent.main` 常驻（`frontend/main/sidecar.ts:25`）。
模块在进程启动时载入 `sys.modules`；**改写磁盘上的 `.py` 不影响已运行进程**。
要让改动生效，唯一可靠方式是**重启 sidecar 进程**。

### 2.4 两条独立的"断连"路径

| 路径 | 触发 | 机制 | 证据 |
|---|---|---|---|
| **A. 后端核心代码** | 改 `backend/private_agent/core/*`、`main.py` 等**已加载模块** | 必须重启 sidecar 才生效 → 重启即断 WS | `sidecar.ts` 常驻进程；无热重载（`uvicorn.run(app, ...)` 无 `reload`） |
| **B. 前端渲染代码** | 改 `frontend/renderer/*` | vite HMR **full reload**（renderer 无 `import.meta.hot.accept`）→ 页面重载 → WS 断 | `grep "import.meta.hot" renderer/` → **零匹配**；vite 默认对非 accepting 模块整页刷新 |

**这解释了"仅核心代码才出问题"**：所谓"核心"= **已加载/正在运行的模块**。
- 新增独立文件（脚本、skill、文档）→ 不需要重载 → 不影响对话 ✓
- 修改已加载模块 → 必须重载 → 断连 ✗

### 2.5 与既有机制的关系（不是崩溃）

- `agent.log` 的 `Sidecar started` 时间点（10:17 / 10:53 / 12:41 / 15:03 / 15:15）
  **全部对应蒋先生的手动重启**，无一例是"改完代码后自动重启"。
- `logs/desktop-launch.log` 显示 Electron 退出码均为 `0`（正常关闭），无崩溃痕迹。
- `main/sidecar.ts` 虽有崩溃自动重启（`MAX_RESTARTS=3`，退避 1s/2s/4s），
  但本次现象**不是崩溃**触发。

**判定：这是架构性限制（自我修改正在运行的进程），不是 bug。**

## 三、根因陈述

> **PA 的自我改动目标是它自己正在运行的进程。改动要生效必须重载该进程，
> 而重载即中断承载"自我改动流程"的那条对话 ——
> 「生效」与「对话连续性」在此架构下天然互斥。**

PA 目前的做法（skill 指令 + 系统提示第 ⑤ 步）是"改完 → 告知用户重启 → 由用户重启"，
把冲突抛给了人；用户重启后，原来的对话上下文与后续步骤已不可见 → 主观感受为"修改失败"。

## 四、优化方案

### P1 · 影子验证：让"改对了"不再依赖重启（推荐先做）

现状：自我修复链路第 ④ 步只有 `code_execution 语法验证`（`py_compile` 级别），**太弱**
——语法通过不等于可导入、更不等于行为正确，所以 PA 无法确信改动有效，只能催着重启看结果。

改为**三层影子验证**（全部在独立进程/沙箱内完成，**主进程零影响**）：

| 层 | 做法 | 拦住什么 |
|---|---|---|
| L1 语法 | `py_compile`（已有） | 语法错 |
| L2 导入 | `python -c "import <module>"`（沙箱 + `sys.path` 指向 backend） | 导入期错误、循环引用、缺依赖 |
| L3 目标测试 | 跑**受影响模块**的单元测试（如改 `react_loop.py` → `pytest tests/test_react_loop.py tests/test_vision_chain_guard.py`） | 行为回归 |

**收益**：PA 改完即知对错，**不需要靠重启来验证** → 不再被迫中断对话。

### P2 · 待生效清单（把"重启"从"流程中"挪到"流程后"）

新增 `pending_changes` 记录（DB 表或 config_runtime 条目）：

```
{file, sha256_after_edit, summary, verified_at, verified_by: "shadow-L3", applied: false}
```

- PA 改完 → 写清单 → **对话继续**（不要求立即重启）
- 下次 PA 启动时**自动核对**（比对文件 sha256）→ 标记 `applied: true` → 日志/首页提示
- 用户随时能看到"有 N 项改动待生效"，择机重启

**收益**：把"改完必须重启"降级为"改完记录，择机重启"。自我改动流程**可以在一次对话内闭环**。

### P3 · 断连后的可恢复性（补强体验）

| 改进 | 说明 |
|---|---|
| 重连自动补发 | 已有 `ws_offset` replay 机制；需确认覆盖"断连期间新产生的 turn 增量" |
| 落库兜底 | 断连期间后端跑完的 turn 已写 `messages`；重连后前端应**主动拉取最后一轮**而非只等推送 |
| 明确归因 | 断连恢复后 UI 提示"**后端已重启（代码生效）**"，而非笼统的"重连中"——避免用户误判为故障 |

### P4 · 前端路径的显式提示

改 `frontend/renderer/*` 必触发整页重载（无 `import.meta.hot`）。
不建议给所有顶层组件加 HMR 处理（状态复杂、易错），而是：

- PA 改前端核心组件时，**主动提示**："前端已更新，页面将重载，当前对话可能中断，
  建议在新对话中验证" —— 把不可控的中断变成**可预期**的操作。

### P5 · 热重载（不推荐，仅备案）

对**白名单模块**（skills / tools 注册表等无长生命周期状态的模块）支持 `importlib.reload`。
**明确排除** `core/react_loop.py`、`main.py` —— 它们持有 WS 连接、会话状态、
asyncio 任务，重载必然造成不一致。

## 六、与其他机制的关系

- **与 `sidecar.ts` 自动重启**：那是**崩溃**兜底（≤3 次），本方案针对的是**主动改动生效**
  的场景，两者正交。建议在崩溃重启时也写入 `_STARTUP_WARNINGS`（已有机制）以便 `/health` 可见。
- **与 `harness.py` skill**：其"改前备份 .bak"是好的工程习惯，**保留**。但建议补充
  "改后走影子验证 + 记入待生效清单"，让 skill 与新流程对齐。
- **与 `code_execution` 沙箱**：影子验证天然适合放在沙箱内（已有隔离、限时、限内存），
  不需新增执行环境。

### 8.1 P0 落地内容（`frontend/main/sidecar.ts`）

- stdout/stderr 全量落盘 → `<workspace>/logs/sidecar.log`（dev=`backend/logs`，
  打包=`userData/logs`）
- `exit` 记录 `code` / `signal` / 时间 / 是否优雅；**崩溃时同步补写输出尾部**
  （内存各留 4KB，规避流式未 flush 导致现场丢失）
- 重启次数用尽时 ERROR 明示常见原因（内存不足 / 端口占用 / 代码异常）
- `spawn` / `health OK` / `graceful stop` 全生命周期时间戳记录
- 修 `stdout` 无人消费的阻塞隐患

> **生效条件**：需重启 PA（`start-dev.mjs` 会自动 `tsc -p tsconfig.main.json`
> 重新编译主进程）。**重启后若再发生崩溃，`sidecar.log` 会给出退出码与 stderr 尾部
> —— 这正是此前完全缺失的现场。**

### 8.2 P1 落地内容（`core/capability_map.py` 的 `CHANNELS_TEXT`）

改前 → 改后：

| 步骤 | 改前 | 改后 |
|---|---|---|
| ④ 验证 | 仅 `code_execution 语法验证` | **影子验证三层**：`py_compile` → `import 目标模块` → **跑受影响模块单测**；明示"绝不允许以重启后看结果代替验证" |
| ⑤ 收尾 | 要求用户"关闭 PA 并重新打包" | **落盘即完成**：告知"已落盘 + 已验证 + 重启后生效"，**不要要求用户立即重启** |
| 认知 | "改完不立即生效，必须等用户重新打包" | **改的是自己正在运行进程的源码；必须重启才生效属正常现象，不是失败** —— 避免误判"没生效=改错了"而反复重改 |
| 前端 | 无 | 改动 `frontend/renderer/*` 会触发 vite 整页重载、可能中断对话，动手前先告知 |

同步修订 `tests/test_system_capabilities.py`：原断言要求输出含"重新打包"——那恰是要
移除的错误指引；改为断言新语义并显式断言过时短语不复存在。
